◆ Engine architecture

Built so a wrong answer costs more than a slow one.

A cache that answers confidently but incorrectly is worse than no cache. Each layer below exists to make an unsafe answer harder to produce than an honest refusal.

Semantic cache, not key lookup

Every phrasing of a complaint is embedded and indexed separately — canonical form, original wording and each paraphrase — so a rewording matches a stored paraphrase rather than missing a single canonical key.

384-dim · HNSW cosine · m=16

Deterministic validation gate

Schema, wording rules and every deeplink URI are checked against the catalog before a plan is served. Cached plans are re-checked on read, because rules tighten and catalogs change after a plan is written.

0 free-text URLs permitted

Ambiguity margin

Similarity alone cannot separate a reworded complaint from a different complaint phrased similarly. The best plan must also beat the runner-up by a margin, or the request is treated as a miss.

threshold 0.78 · margin 0.05

Grounded in supplied text

Steps are derived only from the knowledge-store text attached to the request. With no reference text the engine answers no_siis_context and returns no plan, rather than inventing one from model memory.

never invents a step

Two targets are missed, and they are printed here on purpose.

The cold path is two sequential model calls and costs seconds; the architecture is built to keep traffic off it, but a genuinely novel complaint still pays it. Deeplink coverage is limited by the catalog: only 138 of 578 entries carry a complete validation block, so a validation deeplink is emitted only where the catalog supports one rather than being invented. Step-accuracy and deeplink-relevance scores are left blank in the report because they are human-judged against reference plans the kit does not ship.

◆ Zero-config integration

One POST. One validated plan.

The service is a single FastAPI process. It owns the embedding model, the connection pool, the HNSW indexes and the validation gate, so a caller sends a complaint and its reference text and receives a plan that has already been checked.

  • Strict schema on the way out. The response validates against the contract shipped with the dataset, including the camelCase field names.
  • Reference text in either shape. A raw string or the {title, content} object the dataset uses; both are normalised.
  • Operational metadata attached. Cache hit, similarity, per-stage latency, model and fallback reason travel with every response.

# 1. One process serves the API and this site.
python -m scripts.run_api

# 2. Send a complaint plus its knowledge-store text.
curl -X POST http://127.0.0.1:8000/v1/troubleshoot \
  -H 'Content-Type: application/json' \
  -d '{
    "query": "My Galaxy S24 Ultra screen is completely black",
    "siis_response": { "title": "...", "content": "..." }
  }'

# 3. Plan comes back validated, with the evidence attached.
{
  "response": { "contexts": [ ... ] },
  "meta": {
    "cache_hit": true,
    "similarity": 1.0,
    "latency_ms": 210.4,
    "model": null,
    "fallback": null
  }
