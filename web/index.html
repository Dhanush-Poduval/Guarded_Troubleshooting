How it works

Complaint to verified outcome, in six steps.

Horizontal on a desktop, a vertical timeline on a phone. The same six operations either way.

  1. 1

    Describe the issue

    In the user's own words, with the knowledge-store text that should ground the answer.

  2. 2

    Retrieve grounded context

    Dense and keyword retrieval propose catalog screens together, fused by weighted rank fusion.

  3. 3

    Generate a safe plan

    Actions are extracted from the supplied text, ordered so disruptive steps come last.

  4. 4

    Open the exact setting

    Each step carries a catalog-approved deeplink to the precise screen, not a parent menu.

  5. 5

    Verify the resulting state

    Checked deterministically against the action's own validation contract, where one exists.

  6. 6

    Continue or complete

    On failure, the next action already in the validated plan. Never an invented replacement.

What each result means

The difference between answered and verified.

Five distinct outcomes, never collapsed into a single green tick. This is the system's main guardrail, so the vocabulary is fixed and used identically everywhere.

  • Generated recommendation

    A plan the pipeline produced. It has not yet been checked against anything on a device.

  • Catalog validated

    Schema, wording and every URI pass deterministic checks. The plan is safe to present — not proof that it worked.

  • System verified

    The server read the setting back itself and it matches the expected state. Only evidence the server obtained can reach this.

  • User confirmed

    The user reported the problem fixed. A real outcome, recorded as theirs, and never shown as a system check.

  • Verification unavailable

    No complete validation contract, or no channel to the device. Reported honestly rather than counted as a pass.

This deployment cannot read Galaxy device state.

The catalog ships masked bixby:// URIs and this console is a desktop web page with no channel to a handset, so automatic checks report verification unavailable and outcomes rest on clearly labelled user confirmation. A device-side adapter plugs into the existing interface without changing anything above it.

Integration

One POST. One validated plan.

A single FastAPI process owns the embedding model, the connection pool, the vector indexes and the validation gate, so a caller sends a complaint and its reference text and receives a plan that has already been checked.

  • Strict schema on the way out. The response validates against the contract shipped with the dataset.
  • Reference text in either shape. A raw string or the {title, content} object the dataset uses.
  • Evidence attached. Cache hit, similarity, per-stage latency, model and fallback reason travel with every response.
Full OpenAPI reference
troubleshoot.sh 
# One process serves the API and this site.
python -m scripts.run_api

# Send a complaint plus its knowledge-store text.
curl -X POST http://127.0.0.1:8000/v1/troubleshoot \
  -H 'Content-Type: application/json' \
  -d '{
    "query": "My Galaxy S24 Ultra screen is completely black",
    "siis_response": { "title": "...", "content": "..." }
  }'

# The plan returns validated, with the evidence attached.
{
  "response": { "contexts": [ ... ] },
  "meta": {
    "cache_hit": true,
    "similarity": 1.0,
    "fallback": null
  }
}
